## 一、介绍：端侧定长 & 固定计算图是什么、为什么要这么做

### 1.1 先纠一个最容易误解的点

笔记 02 说的"causal mask 改造"，**改的不是"有没有掩码"，而是"掩码从哪来"**：

| 问题 | 答案 |
|------|------|
| 原始模型有 causal mask 吗？ | **有**，是核心、不可缺 |
| 训练时有吗？ | **有**，训练时尤其必须（否则会偷看答案、学不会预测） |
| 那改造改了什么？ | 只改**生产方式**：模型内部**动态生成** → 由**外部输入**直接喂入 |

> **掩码一直都在**，三个版本（原始/训练/端侧）都有它。改造没删它、也没新增它，只换了"供货渠道"。

### 1.2 "端侧定长输入"是指什么

- **端侧**：模型跑在**手机/终端设备**的 AI 加速芯片（高通 HTP/NPU）上，区别于服务器 GPU。
- **定长输入**：输入张量形状（尤其 seq 长度）**固定写死**，如永远 `[1, 2048]`，不能这次 10、下次 37。

| | GPU（动态） | 端侧 NPU（定长） |
|---|---|---|
| 输入长度 | 想多长多长，框架自动适配 | 编译时固定，如恒为 2048 |
| 短句怎么办 | 按真实长度直接算 | **padding 补齐**到 2048，再用 mask 标记补的部分 |
| 原因 | GPU 灵活、支持动态 shape | NPU 把计算提前编译成固定算子排布，shape 一变要重编译，极慢甚至不支持 |

所以"端侧定长输入" = **不管实际说几个字，模型入口永远收固定大小的张量**（短了补、长了截）。
正因长度固定且已知，**掩码形状也固定**，没必要每次动态算 → 预先算一次当输入喂进去即可。

### 1.3 为什么端侧的输入必须定长？

这不是开发者的偏好，而是**端侧硬件（NPU/HTP）工作方式的硬性前提**。

#### 1. 最核心原因：NPU 是"提前编译好的固定流水线"

| | GPU（动态） | 端侧 NPU/HTP（定长） |
|---|---|---|
| 怎么执行 | 运行时即时调度，shape 多少都能现算 | **编译期就把整张图编成固定指令/算子排布**烧到芯片上 |
| shape 变了 | 无所谓，自动适配 | **要重新编译**（极慢），或干脆不支持 |
| 设计目标 | 通用、灵活 | 极致省电、低延迟、面积小 |

NPU 为了省电和快，砍掉了灵活性：它在**编译期（导出时）就要知道每个张量的确切形状**，据此提前分配内存、规划数据搬运、把算子映射成固定硬件指令。上线后 shape 不能再变——变了之前的规划全失效。

#### 2. 类比：现炒 vs 预制菜流水线

- **GPU 像现炒的厨师**：点什么菜（什么 shape）当场看单现做，灵活但每道都要临时调度，耗电耗资源。
- **NPU 像预制菜流水线**：出厂前就把每个工位、传送带长度、容器大小按**固定规格**调好，又快又省电；但要换尺寸就得**停线重新改造**（重新编译），代价极大。

手机最在意**功耗和延迟**，所以走"预制菜流水线"路线 → 必须定长。

#### 3. 定长换来的好处

形状固定后，编译器能做一堆"形状已知才能做"的优化：

1. **静态内存分配**：每个张量多大、放哪，编译期算死，运行时零分配开销。
2. **算子融合/排布固定**：哪些算子合并、数据怎么在片上缓存搬，全部预规划。
3. **无控制流分支**：不用处理"如果长度是 X 走这条路"，图是直线，流水线不卡顿。
4. **量化更好做**：量化要统计每个激活的数值范围，形状固定才好对齐。

#### 4. 句子长短不一怎么办 → padding + mask

定长的代价用两招补齐：

```
真实输入: "今天天气真好"   (6 个 token)
          ↓ padding 补到固定长度 2048
模型输入: [今天 天气 真 好 <pad> <pad> ... <pad>]   (恒为 2048)
          ↓ 配一个 mask
mask:     [ 1   1   1  1   0    0   ...  0 ]   ← 0 的位置不参与注意力
```

代价：哪怕只说 6 个字也按 2048 规模算（有浪费），但换来**形状固定、可编译、省电快速**。

### 1.4 定长/非定长是怎么影响功耗和延迟的

**核心认知**：端侧功耗和延迟的大头**不在"算"，而在"调度 + 搬数据"**。真正费电费时的是三件事：

1. **数据搬运**（内存 ↔ 片上缓存 ↔ 计算单元来回搬）—— 搬数据能耗常是一次乘法的几十到上百倍。
2. **指令调度 / 控制流**（决定下一步算什么、走哪条分支）。
3. **重新规划 / 编译**（shape 变了要重排内存和指令）。

定长 vs 非定长，差距主要在这三件事上，而不是"算得多算得少"。

#### 非定长（动态）为什么更耗电更慢

| 原因 | 说明 |
|------|------|
| **重新编译/重规划**（最致命） | shape 一变，编译好的指令序列和内存布局全失效 → 要么重编译（几百 ms～秒级），要么硬件不支持。对"逐词生成"这种高频调用是灾难。 |
| **无法预取、流水线断裂** | 运行时才知道下一块多大/在哪 → 计算单元算完得**停下来等**调度和数据 → 空转（占着电不干活）。 |
| **控制流分支卡顿** | `if sequence_length != 1` 这类分支会打断为固定数据流设计的硬件流水线，需额外判断逻辑，增延迟增功耗。 |

流水线对比（定长能无缝重叠，动态会空转等待）：

```
定长(提前知道下一块在哪)：
  计算: [块1][块2][块3][块4]   ← 满负荷不停
  搬运: [块2][块3][块4][块5]   ← 提前预取，无缝衔接

动态(运行时才知道)：
  计算: [块1]__等__[块2]__等__   ← 算完停下来等"下一步是什么"
  搬运:     [块2?]     [块3?]     ← 不敢提前搬，怕白搬
```

#### 定长为什么省电低延迟

形状固定 → 编译期把一切**算死排好**，运行时只管"按图施工"：

| 优化 | 省了什么 |
|------|---------|
| 静态内存分配 | 运行时零分配、零判断 |
| 数据预取 / 流水线 | 计算单元不空转，吞吐拉满 |
| 算子融合 | 减少中间结果搬进搬出（省最贵的搬运能耗） |
| 无分支直线执行 | 流水线不卡顿，时序可预测 |
| 关闭不用的单元 | 其余单元断电省功耗 |

> 一句话：**定长让 NPU 从"边跑边想"变成"按图施工"**——把"想"（调度、判断、重编译）全省了，只剩高效执行。

### 1.5 定长的缺点 & 工程上怎么解决

定长不是没代价，主要有四个缺点，工程上各有成熟解法：

#### 缺点1：短输入的算力浪费（最常见）
只说 6 个字，也按固定长度（如 2048）整体算一遍 → 大量算力花在 `<pad>` 上。

**怎么解决：**
- **分桶（bucketing / 多档定长）**：不是只编一个 2048 的图，而是编译**几档**固定长度（如 128 / 512 / 1024 / 2048），运行时按实际长度选**最接近的那一档**，把浪费控制在一档之内。
- **prefill 与 decode 分两张图**：prefill（首次处理整段 prompt）用一个较长的定长图并行算；decode（逐词生成）用 seq=1 的小图，每次只算一个新词。两阶段各自定长、互不浪费。

#### 缺点2：超过最大长度就放不下
定长有上限（如 2048），prompt + 生成超了怎么办？

**怎么解决：**
- **滑动窗口 / 截断**：只保留最近 N 个 token，老的丢弃或滚动。
- **分段 prefill（chunked prefill）**：长 prompt 切成固定大小的块，逐块喂入、KV Cache 累积，绕过"单次必须放下全部"的限制。

#### 缺点3：KV Cache 也得定长，占显存/内存
端侧 KV Cache 常预分配成定长（最大长度），即使实际只用一点，内存也按最大占。

**怎么解决：**
- **定长预分配 + 写指针**：开一块最大长度的缓存，用 `cache_position` 指针标记写到哪，只在有效区算（本项目 `return_new_key_value_only` / 定长 KVCache 改写正属于此类）。
- **量化 KV Cache**：把 K/V 也量化到低位宽，按比例省内存。

#### 缺点4：多档图带来管理/存储成本
分桶会编译出多张图，包变大、维护变复杂。

**怎么解决：**
- **档位取舍**：只保留少数几个高频档位（覆盖绝大多数请求），其余向上取整到最近档。
- **权重共享**：多档图共享同一份权重，只是输入 shape 和计算图结构不同，避免权重重复存储。

> 小结：定长的缺点几乎都源于"形状被钉死"，工程解法的共同思路是 **"用有限的几档定长 + 分阶段(prefill/decode) + 滑窗/分块"**，在"灵活性"和"可编译高效"之间取平衡——既保住定长带来的省电低延迟，又把浪费和上限问题压到可接受范围。

## 二、原理

### 2.1 网络结构 vs 计算图（先分清"模型内部"到底指谁）

聊"定长导出""模型内部 shape 恒定"时，"模型内部"这个词很容易被误解成"网络结构"。先把三个词分清，后面所有定长讨论才不糊：

| 说法 | 是什么 | 含不含具体序列长度 |
|------|--------|------------------|
| **网络结构** | 有哪些层、怎么连（Attention→MLP→…）、权重多大 | **不含**——结构对长度"无所谓" |
| **计算图（前向）** | 拿一个**具体形状的输入**，把网络结构"跑一遍"记录下的算子 + 张量流 | **含**，长度被写死，如 `[1,32,128,1023]` |
| **导出的 ONNX/端侧图** | 上面那张计算图被固化、编译成端侧能跑的东西 | 形状全部冻结成常数 |

> 我们说的**"模型内部" = 中间那个"计算图"**（网络结构 + 一组具体输入形状 trace 出来的前向过程），**不是**抽象的网络结构。

**为什么强调是计算图？** 因为**网络结构本身根本不关心序列多长**：

```
网络结构（不含长度） ──喂一个具体形状的dummy输入去trace──▶ 计算图（长度被写死）──编译──▶ 端侧图
      ↑                                                       ↑
  同一套Qwen2，喂seq=100或1000都能算              长度这个数字是在这一刻才被焊进去的
```

同一套 Qwen2 结构（层、权重完全不动），喂 `seq=100` 或 `1000` 都能算——结构是通用的。真正把"长度"焊进去的，是你用某个具体输入去 trace（`torch.onnx.export` 的 jit tracing）出来的那张图。

**这对本项目的两处改造意味着：**
- 掩码改造 / KV Cache 改写，**改的都不是"结构长相"**（层还是那些层），而是 **forward 里数据怎么流**，从而决定 **trace 出来的那张图形状是否恒定**。
- 官方动态 mask / `DynamicCache`：结构没错，但每次 trace 出的图里 shape 是变的（10×10→2048×2048、K 长度 100→101→102）→ 图不定长 → 编译失败。
- 端侧改写：保证**每次 trace 出的图都是同一套固定形状** → 能编译成一张端侧反复跑的定长图。

> 一句话：定长与否的战场在**计算图**，不在网络结构；改造的目标就是让"每次 trace 出的图形状恒定"。KV Cache 侧的落地细节见 [附录K · 4.4 节](./02-附录K-KV%20Cache(键值缓存).md#44-只存新-kv为什么反而能定长导出)。

### 2.2 "导出固定计算图"是什么

#### 计算图
模型的一连串运算（矩阵乘、加、softmax、reshape……）可画成有向图：节点=算子，边=数据流。

```
输入 ─▶ q_proj ─▶ +mask ─▶ softmax ─▶ ×V ─▶ o_proj ─▶ 输出
```

#### 导出
把 PyTorch 模型转成标准、独立的图格式文件（**ONNX**），脱离 Python，交给端侧引擎(QNN/QAIRT)跑。即 README 流程图最后的"导出 ONNX"。

#### 为什么要"固定"
导出时引擎希望图是**静态、结构写死**的——每个算子输入输出 shape 确定、没有"看情况而定"的分支。但官方动态生成 mask 那段里有（代码见第三节）：

- `if sequence_length != 1:` → **控制流分支**（图里出现"如果…否则…"）
- `torch.full / triu / arange` 依赖运行时长度 → **动态 shape**

这些导出到 ONNX 会变成丑陋的动态子图，端侧 HTP **不友好甚至跑不了**。

## 三、官方 Qwen2 的做法：causal mask 怎么"动态生成"

"动态" = 每次 forward 时，**按本次输入的实际长度，临时用代码现场算出掩码矩阵**。官方 `modeling_qwen2.py` 第 1113-1119 行核心：

```python
# sequence_length = input_tensor.shape[1]   ← 读出本次输入的实际长度（动态的根源）
causal_mask = torch.full((sequence_length, target_length), min_dtype)  # 先全部置为极小负数
if sequence_length != 1:
    causal_mask = torch.triu(causal_mask, diagonal=1)   # 取上三角→形成"挡住未来"的下三角形状
causal_mask *= torch.arange(target_length) > cache_position.reshape(-1, 1)  # 结合KV Cache修正
causal_mask = causal_mask[None, None, :, :].expand(B, 1, -1, -1)  # 扩出 batch/head 维
```

| 步骤 | 动作 | 直觉 |
|------|------|------|
| `input_tensor.shape[1]` | 读出本次输入长度 | 长度运行时才知道 → "动态" |
| `torch.full(..., min_dtype)` | 建全是极小负数的方阵 | 先假设全部屏蔽 |
| `torch.triu(diagonal=1)` | 上三角保留负数、其余清零 | 这就是"挡住未来"的下三角 |
| `arange > cache_position` | 结合历史长度再修正 | 推理时历史 token 不该被挡 |
| `[None,None].expand(B,...)` | 变成 `[B,1,seq,seq]` | 好加到注意力分数上 |

**关键**：掩码形状由 `input_tensor.shape[1]` 决定，输入 10 就建 10×10、2048 就建 2048×2048，**每次 forward 重跑一遍** → 这就是"动态生成"。

> 端侧改造的 `bypass_update_causal_mask` 把这一整段**全删了**，直接 `return attention_mask`（外部传入的现成掩码），见下一节。

## 四、本项目改造后的做法：把 mask 当外部输入（bypass）

### 4.1 把"生成 mask"从图内部挪到图外部

导出成固定计算图的办法，就是把"生成 mask"从**图内部**挪到**图外部**：

```
官方：  [输入] ─▶ (图里现场构造mask的一堆算子) ─▶ 注意力 ...   ← 有分支/动态shape
端侧：  [输入] + [mask作为另一个输入] ─▶ 注意力 ...           ← 图里只剩干净固定算子
```

mask 作为模型的**一个外部输入**直接喂入，导出的 ONNX 图就**纯静态、形状全固定、无分支** → 这就是"导出固定计算图"。

### 4.2 三者的因果链（串起来记）

```
端侧定长输入(长度固定)
      │
      ▼
掩码形状也固定 → 没必要在模型里动态生成
      │
      ▼
把 mask 当外部输入喂进来 (bypass_update_causal_mask)
      │
      ▼
导出的计算图无动态分支 → 固定计算图(ONNX) → 端侧高效跑
```

> `bypass_update_causal_mask`（那 3 行）就是这条链的落地：删掉动态生成、改成透传外部 mask。对应 config 的 `use_combined_mask_input`。

## 五、记忆锚点

- **动态生成**：按 `input_tensor.shape[1]` 现场用 `full+triu` 建掩码，每次 forward 重算。
- **端侧定长**：输入 seq 固定写死（如 2048），短句 padding 补齐 + mask 标记。
- **为什么定长**：NPU 是"预制菜流水线"，编译期就要知道确切形状才能省电提速；shape 变就得重编译。
- **功耗/延迟大头**：在"搬数据 + 调度 + 重编译"，不在"算"。定长可预取、可流水线、不重编译 → 省。
- **定长缺点**：短输入浪费、超长放不下、KV Cache 占内存、多档图管理成本；解法=分桶多档 + prefill/decode 分图 + 滑窗/分块。
- **固定计算图**：导出成无分支、无动态 shape 的静态 ONNX，端侧才好跑。
- **网络结构 vs 计算图**：定长战场在"计算图"（trace 出的前向），不在网络结构。
- **一句话**：定长 → 形状固定 → 不必动态生成 → mask 外部喂入 → 图变静态。
