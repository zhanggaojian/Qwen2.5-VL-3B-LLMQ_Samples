# 00-基础篇 · 模型是什么 & 推理的两个阶段(prefill / decode)

> **定位**：整个学习笔记的**地基第一篇**。后面所有笔记（模型适配、量化、导出）都建立在"模型是一套权重、推理分两阶段"这个认知上。先把这篇看懂，再往下看不容易绕晕。
> **一句话本质**：**模型只有一套**（一堆层 + 一套权重）；**推理时分 prefill 和 decode 两个阶段**用它，但跑的是**同一个模型**。所谓"模型改造"改的是**模型本身**，两个阶段都共享。
>
> **本篇结构（四段式）**：一 介绍（模型是什么）→ 二 原理（推理为什么分两阶段、两阶段怎么回事）→ 三 官方/通用做法（标准推理就是同一个模型跑两阶段）→ 四 本项目改造后的做法（改造作用在哪 + 端侧导出两张图）。

---

## 一、介绍：模型是什么（先建立最朴素的认知）

一个大语言模型(LLM)，剥开看就是：

```
一堆相同结构的层(Decoder Layer)叠在一起，每层 = Attention + MLP
        +
一套训练好的权重(参数)
```

- 它的唯一本领：**给定前面的 token，预测下一个 token 的概率**。
- 它**不是**一个"程序流程"，没有内置"先做 A 再做 B"的阶段划分。它就是一个**函数**：输入一串 token → 输出每个位置"下一个词"的预测。

> 记住这点：**模型本身不区分 prefill / decode**。这两个词描述的是"我们怎么调用它"，不是它内部的结构。

---

## 二、原理：推理为什么分两阶段、两阶段怎么回事

### 2.1 为什么推理要分两个阶段

模型是**自回归**的（见 [02-附录D-自回归与自注意力.md](./02-附录D-自回归与自注意力.md)）——一个词一个词往外蹦。但"蹦"之前，得先把用户给的那段话(prompt)读进去。于是自然分成两步：

| 阶段 | 干什么 | 一次喂几个 token | 类比 |
|------|--------|----------------|------|
| **prefill（预填充）** | 把整段 prompt **一次性并行**读进去、建立上下文 | 多个（整段，如 20 个） | 读题：把题目一口气读完 |
| **decode（解码）** | **逐个**生成新词，每次只算 1 个 | 1 个 | 答题：一个字一个字往外写 |

完整过程：

```
用户输入: "今天天气怎么样"
   │
   ▼  ① prefill：7个token 一次性进模型 → 建好 KV Cache → 预测第1个新词"今"
   │
   ▼  ② decode：把"今"喂进去(1个) → 预测"天"
   ▼     decode：把"天"喂进去(1个) → 预测"很"
   ▼     decode：...逐词，直到生成 <eos> 停止
   │
   ▼  输出: "今天很晴朗"
```

**关键**：①②用的是**同一个模型、同一套权重**。区别只有一个——**这次喂进去几个 token**。

---

### 2.2 训练为什么不分 prefill / decode（训练 vs 推理）

**prefill / decode 的划分是"推理（生成）"特有的，训练里没有这个概念。** 原因是两者的处境完全不同：

| | 训练 | 推理（生成） |
|---|------|-------------|
| 后面的词 | **已知**（数据集里就是完整句子）| **未知**，要一个个"造"出来 |
| 怎么跑 | **teacher forcing**：整句一次性并行喂入，做**一次前向**就算完所有位置 | 自回归循环：prefill 读 prompt + decode 逐词生成 |
| 有几次前向 | 1 次（整句） | 1 次 prefill + N 次 decode |
| 分阶段吗 | **不分**（没有"逐词生成"的循环）| 分 prefill / decode |

训练用 **teacher forcing**：因为整句答案已知，可以把整个序列一次并行喂进去、一次前向算完所有位置的 loss，不需要"生成一个→接回去→再生成"。

```
训练（一次前向，并行）:
输入:  [今天 天气 真 好 <eos>]     ← 整句一次性喂入
        ↓ 一次 forward
     每个位置都预测"下一个词"，所有位置 loss 一起算、一次反向传播
```

**两个推论**：

1. **训练用不上 KV Cache**。训练一次前向就算完整句，不存在"跨步复用历史 K/V"；而且每步反向后权重都变了，缓存也会失效。KV Cache 只在**推理的 decode 阶段**才有价值（见 [附录K](./02-附录K-KV%20Cache(键值缓存).md)）。
2. **prefill ≈ 一个大号的训练前向**。prefill 那一步也是"整段并行 + causal mask"，算法上几乎等同训练的一次前向，区别只是它不算 loss、不反向，而是把 K/V 存进缓存、吐出第一个新词。训练里真正没有的是后面的 **decode 循环**。

> ⚠️ 别混的一点：**因果掩码训练时反而更不能少**。正因训练整句并行喂入，位置 `i` 物理上够得到后面的词，必须靠掩码挡住未来，否则"偷看答案"、学不会预测（见 [附录E](./02-附录E-端侧定长与计算图导出.md) 开头）。掩码训练/推理两边都要，只是形状不同（详见 2.4）。

**一句话**：训练 = 一次并行前向（teacher forcing），无阶段、无 KV Cache，但要 causal mask；推理 = prefill（≈训练式前向）+ decode 循环，才引出 prefill/decode 和 KV Cache。

---

### 2.3 用"榨汁机"类比彻底理解

> 模型像一台**榨汁机**：
> - **prefill** = 一次性把一整袋水果倒进去榨（处理整段 prompt）。
> - **decode** = 之后每次只丢一颗新水果进去榨（每次生成 1 个新词）。
>
> 榨汁机（模型）**自始至终是同一台**，没有"prefill 版"和"decode 版"两台机器。区别只是**你每次放多少进去**。

所以：
- ❌ 错误理解："模型分成 prefill 模块和 decode 模块"
- ❌ 错误理解："有两个模型，一个负责 prefill 一个负责 decode"
- ✅ 正确理解："**一个模型，被以两种方式（喂多个 / 喂一个）调用**，对应推理的两个阶段"

---

### 2.4 两个阶段的细节差异

虽然是同一个模型，但因为输入长度不同，几个地方表现不同：

| | prefill | decode |
|---|---|---|
| 输入 token 数 | 整段 prompt（如 20） | 1 个（刚生成的新词） |
| 走的模型 | **同一个** | **同一个** |
| KV Cache | **第一次填充**（建立历史 K/V） | **读历史 + 追加 1 个** |
| 因果掩码 | 完整下三角 `[seq, seq]` | 退化成一行 `[1, 历史长度]`（几乎全可见） |
| 计算量 | 大（一次算整段） | 小（每次只算 1 个词） |

> 因果掩码在两阶段的差异详见 [02-附录E](./02-附录E-端侧定长与计算图导出.md)；为什么 decode 的掩码几乎全通——因为"未来"还没生成出来，天然没有需要遮挡的未来。

## 三、官方 / 通用做法：标准推理就是同一个模型跑两阶段

上面第二节讲的 prefill / decode 划分，本身就是**官方 / 通用的做法**——HuggingFace、vLLM 等任何推理框架跑生成时都是这个流程：**同一套权重的模型**，先用 prefill 并行读入 prompt、建好 KV Cache，再用 decode 逐词生成。模型只有一个、**不区分两阶段**，两阶段只是"我们怎么调用它"。

本项目**沿用这一划分不变**（照样是 prefill + decode），真正的改动只有两处，都在下一节：**① 换掉模型内部零件（量化专用），② 因端侧定长把同一模型导出成两张静态图**。

---

## 四、本项目改造后的做法：改造作用在哪 + 端侧导出两张图

### 4.1 "模型改造"作用在哪？（最容易混淆的点）

本项目的核心是**模型改造（Monkey Patch）**——把官方模型的零件换成端侧量化专用版（见 [02-模型适配(Monkey-Patch).md](./02-模型适配(Monkey-Patch).md)）。

**改造改的是"模型本身"，所以 prefill 和 decode 两个阶段都用到、都共享。**

```
            ┌─────────────────────────┐
            │   改造后的模型(一套)     │   ← Monkey Patch 改的是这里
            │  Conv版Attn + 外部mask   │      (改的是零件/权重，不分阶段)
            │  + 定长KV Cache ...      │
            └───────────┬─────────────┘
                        │ 同一个模型，两种调用方式
          ┌─────────────┴──────────────┐
          ▼                             ▼
   prefill 阶段                    decode 阶段
   (喂整段prompt)                  (每次喂1个词)
```

所以回答常见疑问：
- **"改造是用于 prefill 还是 decode？"** → 都用。改造改在模型上，两阶段共享。
- **"模型本身分 prefill 和 decode 吗？"** → 不分。是**推理过程**分两阶段，跑的是同一个模型。

---

### 4.2 端侧的特殊点：同一个模型导出成"两张图"

这一点是很多人困惑的根源。端侧要求**定长**（输入形状固定，见 [02-附录E](./02-附录E-端侧定长与计算图导出.md)）——但 prefill 输入长（如 128）、decode 输入只有 1，**长度不一样**！而一张定长计算图只能固定一种形状。

工程做法：**从同一个改造后的模型，导出两张定长图**：

| | prefill 图 | decode 图 |
|---|---|---|
| 输入 shape | `[1, 较长]`（如 128） | `[1, 1]` |
| 掩码 shape | `[128, 128]` 下三角 | `[1, max_len]` 单行 |
| 权重 | **共享同一套** | **共享同一套** |

⚠️ 关键：**这不是两个模型，是同一套权重因输入长度不同被"拍扁"成两张形状不同的静态图**。拆两张纯粹是"定长"的工程要求，不是算法上有两个模型。

---

## 五、整条线串起来（全景）

```
1. 模型 = 一套权重的网络(被 Monkey Patch 改造过)   ← 改造改在这层，不分阶段
        │
2. 推理时分两阶段「用」它：
   ① prefill：整段 prompt 一次性进 → 建好 KV Cache
   ② decode ：逐个词进，每次 1 个 → 读 KV Cache + 追加
        │
3. 端侧因为要「定长」，把这同一个模型
   导出成 prefill 图 和 decode 图 两张静态图(共享权重)
```

---

## 六、记忆锚点

- **模型只有一套**：一堆层 + 一套权重，本质是"预测下一个 token"的函数，**不分阶段**。
- **推理分两阶段**：prefill（整段一次性读）+ decode（逐词生成），但跑**同一个模型**。
- **训练不分阶段**：teacher forcing 整句一次并行前向，无 prefill/decode、无 KV Cache，但 causal mask 更不能少；prefill ≈ 一个大号训练前向。
- **榨汁机类比**：同一台机器，prefill 倒一整袋、decode 每次丢一颗。
- **改造在模型本身**：prefill / decode 两阶段共享同一套改造后的零件和权重。
- **端侧两张图**：因定长把同一模型导成 prefill 图 + decode 图，**共享权重，不是两个模型**。
