# 03 · 附录B · mmap 与数据搬运路径

> **关联**：[03-附录A-模型权重文件格式](./03-附录A-模型权重文件格式.md) 中提到 SafeTensors 可以利用 `mmap` 按需访问权重；本篇解释 `read/write/mmap` 背后的页缓存、虚拟内存、物理内存与 DMA。
> **一句话本质**：普通 `read/write` 通常要在“用户缓冲区”和“内核页缓存”之间做一次 CPU 拷贝；`mmap` 把文件区间映射到进程虚拟地址区间，让程序通过页表直接访问文件页缓存，从而省掉这次拷贝。

> **本篇为背景概念篇，按三段式组织**：**① 介绍（先分清磁盘、内存和缓冲区）→ ② 原理（read/write/mmap 的完整路径）→ ③ 对比与实践**。「官方/本项目改造」不涉及。

---

## 一、介绍：先分清“数据在哪里”

### 1.1 内核缓冲区本身就在内存中

最容易产生的误解是把“内存”和“内核缓冲区”看成两个硬件位置。实际上，内核页缓存和用户缓冲区都位于物理内存（RAM）中，只是由不同主体管理、映射到不同的虚拟地址空间。

```text
磁盘 / SSD                         物理内存 RAM
┌──────────┐             ┌────────────────────────────┐
│ 文件持久化数据 │             │ 内核管理区域                 │
└──────────┘             │   └─ 文件页缓存（page cache） │
                         │                            │
                         │ 用户进程可访问区域             │
                         │   └─ char buf[] 等用户缓冲区   │
                         └────────────────────────────┘
```

因此，“从磁盘搬到内核缓冲区”就是：

```text
磁盘 / SSD → RAM 中由内核管理的页缓存
```

并不存在一次额外的“磁盘 → 内存 → 内核缓冲区”搬运。

### 1.2 四个核心概念

| 概念 | 是什么 | 是否真实保存数据 |
|---|---|---|
| 磁盘 / SSD | 持久化存储设备 | 是 |
| 物理内存 RAM | CPU 可直接访问的工作内存 | 是 |
| 虚拟地址 | 进程看到的地址编号，由页表翻译 | 否，它是地址空间 |
| 页缓存 page cache | 内核使用 RAM 缓存文件内容 | 是，占用物理页 |

还要区分三个动作：

- **数据搬运**：把字节从一个存储位置传输到另一个位置。
- **地址映射**：建立“虚拟页 → 物理页”的页表关系，本身不复制文件数据。
- **地址翻译**：CPU 的 MMU 根据页表把虚拟地址翻译成物理地址，也不是数据复制。

### 1.3 谁负责搬运

| 路径 | 通常由谁完成 | 说明 |
|---|---|---|
| 存储设备 → RAM | 存储控制器通过 DMA | 读盘；CPU 负责提交和管理 I/O 请求 |
| RAM → 存储设备 | 存储控制器通过 DMA | 脏页回写；CPU 负责提交请求 |
| 内核页缓存 → 用户缓冲区 | CPU 执行内存复制 | Linux 中可理解为 `copy_to_user()` |
| 用户缓冲区 → 内核页缓存 | CPU 执行内存复制 | Linux 中可理解为 `copy_from_user()` |
| 虚拟地址 → 物理地址 | MMU + 页表 | 只是地址翻译，不搬运数据 |
| 缺页异常处理 | CPU 进入内核，由内核处理 | 必要时再发起设备 DMA 读取 |

> **DMA（Direct Memory Access）**：设备控制器可以直接在设备和 RAM 之间传输数据，CPU 不需要逐字节执行复制指令。但 CPU/内核仍要准备缓冲区、提交请求、处理完成通知和维护文件系统状态。

## 二、原理：read、write 与 mmap 的完整路径

### 2.1 普通 `read()`：页缓存未命中

示例：

```c
char buf[4096];
ssize_t n = read(fd, buf, sizeof(buf));
```

如果所需文件页不在页缓存中：

```text
磁盘 / SSD
    │
    │ ① DMA：设备 → RAM
    ▼
内核页缓存
    │
    │ ② CPU：copy_to_user()
    ▼
用户缓冲区 buf
```

过程如下：

1. 用户进程调用 `read()`，CPU 从用户态进入内核态。
2. 文件系统检查目标文件页是否已在页缓存中。
3. 缓存未命中时，内核向存储设备提交读取请求。
4. 存储控制器通过 DMA 把数据写入 RAM 中的页缓存物理页。
5. 内核通过 CPU 把数据从页缓存复制到用户缓冲区 `buf`。
6. `read()` 返回实际读取的字节数。

这里通常有一次设备到 RAM 的 DMA，以及一次 RAM 内部的 CPU 拷贝。

### 2.2 普通 `read()`：页缓存命中

如果目标文件页已经在页缓存中：

```text
内核页缓存
    │
    │ CPU：copy_to_user()
    ▼
用户缓冲区 buf
```

此时不访问存储设备，也没有设备到 RAM 的 DMA；但页缓存到用户缓冲区的 CPU 拷贝仍然存在。

这也是为什么“第二次读同一个文件”通常更快：它可能只读 RAM，不再读盘。

### 2.3 普通缓冲式 `write()`

示例：

```c
ssize_t n = write(fd, buf, sizeof(buf));
```

典型路径与 `read()` 相反：

```text
用户缓冲区 buf
    │
    │ ① CPU：copy_from_user()
    ▼
内核页缓存（标记为脏页）
    │
    │ ② 稍后 DMA：RAM → 设备
    ▼
磁盘 / SSD
```

通常过程如下：

1. 内核通过 CPU 把用户数据复制到页缓存。
2. 对应缓存页被标记为脏页。
3. `write()` 通常可以先返回，此时数据未必已经持久化到设备。
4. 内核后台回写线程稍后提交写请求。
5. 存储控制器通过 DMA 把 RAM 中的脏页写到设备。

如果程序要求等待数据落盘，可根据持久化要求使用 `fsync(fd)`、`fdatasync(fd)`，或以 `O_SYNC/O_DSYNC` 模式打开文件。它们主要改变“何时等待写回完成”，不会把页缓存到用户缓冲区之间的 CPU 拷贝变成 DMA。

### 2.4 `mmap()` 到底建立了什么

`mmap()` 本身是一个系统调用。用户程序调用它时会进入内核，由内核在当前进程中创建文件映射；调用返回后，程序得到的是一段**用户虚拟地址**。

示例：

```c
int fd = open("data.bin", O_RDWR);

void *addr = mmap(
    NULL,
    4096,
    PROT_READ | PROT_WRITE,
    MAP_SHARED,
    fd,
    8192
);
```

这表示把“文件从偏移 8192 开始的 4096 字节”映射到进程的一段虚拟地址区间：

```text
addr + 0     ↔ 文件偏移 8192
addr + 100   ↔ 文件偏移 8292
addr + 4095  ↔ 文件偏移 12287
```

`mmap()` 成功时，内核主要创建一段虚拟内存区域（VMA）并记录：

- 虚拟地址起点与长度；
- 对应文件和文件偏移；
- 读、写、执行权限；
- `MAP_SHARED` 或 `MAP_PRIVATE` 等映射类型。

此时通常只是建立了映射规则，并不保证文件数据已经读入 RAM，也不保证所有虚拟页都已有物理页。

#### 2.4.1 最容易混淆的映射关系

`mmap()` **不是**把用户虚拟地址直接映射到内核虚拟地址：

```text
错误理解：用户虚拟地址 → 内核虚拟地址 → 物理内存
```

正确理解是，用户页表把用户虚拟页映射到页缓存所在的物理页。内核为了管理和访问这份数据，也可以在自己的地址空间中映射同一个物理页：

```text
用户虚拟地址 ─────┐
                  ├──→ 页缓存所在的同一个物理内存页
内核虚拟地址 ─────┘
```

这里需要分清三层关系：

```text
文件区间
   │ mmap 的文件映射规则
   ▼
进程用户虚拟地址区间
   │ 页表 + MMU 地址翻译
   ▼
页缓存所在的物理内存页
```

- **文件区间 ↔ 用户虚拟地址区间**：由 `mmap()` 创建的 VMA 记录，是一种映射规则。
- **用户虚拟页 → 物理页**：由页表记录，通常在实际访问并处理缺页后建立。
- **用户虚拟地址 → 物理地址**：由 CPU 的 MMU 在每次内存访问时完成翻译，不复制数据。
- **内核虚拟地址 → 同一物理页**：供内核管理数据，不意味着用户获得了访问内核地址空间的权限。

因此，“用户空间直接读取页缓存”更准确的含义是：程序通过自己的用户虚拟地址，访问页缓存对应的物理页；它没有绕过权限隔离，也不能访问任意内核虚拟地址。

### 2.5 首次访问 mmap 地址：缺页异常 + 按需加载

程序第一次读取：

```c
char value = ((char *)addr)[100];
```

可能发生如下过程：

```text
CPU 访问虚拟地址 addr+100
           │
           ▼
页表中尚无有效物理页映射
           │
           ▼
触发缺页异常（page fault）
           │
           ▼
内核查找文件对应页是否在 page cache
       ┌───┴──────────────┐
       │                  │
    已缓存              未缓存
       │                  │
       │            设备 DMA 到 RAM
       │                  │
       └──────┬───────────┘
              ▼
建立页表：虚拟页 → 页缓存物理页
              │
              ▼
CPU 重新执行原来的内存访问指令
```

建立关系后，路径可以理解为：

```text
进程虚拟地址
      │ MMU 查页表（地址翻译，不复制数据）
      ▼
页缓存对应的物理内存页
      │
      ▼
文件中的对应页
```

映射是按“页”管理的，并不是“整个文件对应一个虚拟地址和一个物理地址”：

```text
虚拟页 0 → 物理页 A → 文件页 2
虚拟页 1 → 物理页 B → 文件页 3
虚拟页 2 → 暂未加载
```

在内存压力下，干净的文件页可以被回收，相关页表项也可以失效。以后再次访问时再触发缺页并重新建立映射，因此物理页并非永久固定。

### 2.6 为什么 mmap 被称为“零拷贝”

普通 `read()`：

```text
磁盘 → 页缓存 → 用户缓冲区
       DMA       CPU 拷贝
```

`mmap()`：

```text
磁盘 → 页缓存物理页 ← 进程虚拟地址通过页表直接访问
       DMA            不再复制到另一份用户 buf
```

`mmap()` 省掉的主要是：

```text
内核页缓存 → 用户缓冲区
```

所以“零拷贝”并不表示完全没有数据搬运：

- 缓存未命中时，文件数据仍要从设备 DMA 到 RAM；
- CPU 仍要处理缺页异常和维护页表；
- 写入的脏页最终仍要从 RAM DMA 回设备；
- 只是避免了页缓存与额外用户缓冲区之间的那次 CPU 拷贝。

### 2.7 mmap 写入：`MAP_SHARED` 与 `MAP_PRIVATE`

```c
((char *)addr)[100] = 'A';
```

两种常见映射语义：

| 类型 | 第一次读取 | 写入时 | 是否写回原文件 |
|---|---|---|---|
| `MAP_SHARED` | 映射文件页缓存 | 修改共享文件页并形成脏页 | 可以，由系统回写；可用 `msync()`请求同步 |
| `MAP_PRIVATE` | 开始时可共享文件物理页 | 写时复制（COW），创建进程私有匿名页 | 不写回原文件 |

`MAP_PRIVATE` 的“私有”不是在 `mmap()` 时立刻复制完整文件，而是通常等到某一页第一次被写入时才复制该页。

## 三、对比与实践

### 3.1 read/write/mmap/O_DIRECT 对比

| 方式 | 是否使用页缓存 | 用户态与内核态数据复制 | 典型特点 |
|---|---|---|---|
| 普通 `read()` | 是 | 页缓存 → 用户 buf，CPU 拷贝 | 接口简单，适合顺序读取、小文件和流式处理 |
| 普通 `write()` | 是 | 用户 buf → 页缓存，CPU 拷贝 | 可延迟回写，吞吐高；返回不等于已落盘 |
| `mmap()` | 是 | 通常不需要额外用户 buf 拷贝 | 按需分页，适合随机访问、大文件、共享文件页 |
| `O_DIRECT` | 通常绕过 | 可让设备直接 DMA 到/从用户页 | 对地址、长度、偏移常有对齐要求，缓存管理交给应用 |

`O_DIRECT` 并不必然比页缓存更快。它适合数据库等自带缓存管理的程序；普通应用如果重复读取数据，操作系统页缓存通常更省事。

### 3.2 mmap 的收益与代价

**主要收益**：

- 减少页缓存到用户缓冲区的一次 CPU 拷贝；
- 像访问数组一样随机访问文件；
- 按需加载，只访问用到的文件页；
- 多个进程可以共享同一份文件页缓存；
- 适合 SafeTensors 这类“头部记录张量偏移、数据区连续”的文件格式。

**需要注意**：

- 首次访问可能触发缺页，延迟不像普通函数调用那样直观；
- 大量随机访问可能产生很多缺页和随机 I/O；
- 文件被并发截断时，继续访问失效映射可能触发 `SIGBUS`；
- 映射长度、文件偏移和页对齐需要正确处理；
- `MAP_SHARED` 的可见性、落盘时机与并发同步是不同问题；
- 使用结束后应调用 `munmap()`，文件描述符也应调用 `close()`。

### 3.3 SafeTensors 为什么适合 mmap

SafeTensors 文件可粗略理解为：

```text
┌─────────────────────────────┐
│ JSON 头：张量名、dtype、shape、偏移 │
├─────────────────────────────┤
│ tensor A 的连续字节                │
├─────────────────────────────┤
│ tensor B 的连续字节                │
└─────────────────────────────┘
```

读取程序先从头部知道某个张量位于文件的哪个字节区间，然后可以只访问对应映射区间。操作系统按页把真正访问到的数据加载进 RAM，不需要先把整个权重文件读进一个额外的大缓冲区。

但要区分两层：

1. **文件读取层**：`mmap` 可以避免 `read()` 到额外用户缓冲区的拷贝，并支持按需加载。
2. **框架张量层**：后续是否还发生 dtype 转换、设备迁移（如 CPU → GPU/NPU）、布局转换或主动复制，取决于框架实现和调用方式。

所以“SafeTensors 支持 mmap”不等于“模型加载和推理全链路完全零拷贝”。

### 3.4 常见误区纠正

| 误区 | 正确理解 |
|---|---|
| 内核缓冲区不在内存里 | 页缓存就是 RAM 中由内核管理的物理页 |
| `mmap()` 立即把整个文件读入内存 | 通常只建立映射规则，访问时按页加载 |
| `mmap()` 把用户地址映射到内核虚拟地址 | 用户虚拟页通过页表映射到页缓存物理页；内核可另外映射同一物理页 |
| 用户直接读取页缓存等于进入内核空间 | 用户仍使用自己的虚拟地址和用户权限，只是该地址最终指向页缓存物理页 |
| 一个虚拟地址对应整个文件 | 映射是一段虚拟地址范围，并按页关联文件页 |
| 虚拟页映射物理页就是复制数据 | 页表映射只是建立地址关系 |
| 所有数据搬运都由 DMA 完成 | 设备与 RAM 之间通常用 DMA；两块 RAM 之间的普通用户/内核复制通常由 CPU 完成 |
| “零拷贝”表示没有任何搬运 | 它通常只表示省掉某一层中间复制 |
| `write()` 返回就是已经落盘 | 普通缓冲写通常只是进入页缓存，持久化需关注 `fsync` 等语义 |

## 四、记忆锚点

- **内核页缓存就在 RAM 中**，不是内存之外的另一个地方。
- **设备 ↔ RAM**：通常由存储控制器通过 DMA 搬运；CPU 负责发起和管理请求。
- **页缓存 ↔ 用户 buf**：普通 `read/write` 通常由 CPU 执行内存复制。
- **mmap 本身先建规则**：文件区间 ↔ 进程虚拟地址区间；不一定马上分配物理页或读盘。
- **不是映射内核地址**：用户虚拟地址和内核虚拟地址可以分别指向同一页缓存物理页，用户始终受用户态权限约束。
- **首次访问可能缺页**：内核查页缓存，未命中则发起 DMA，之后建立页表映射。
- **MMU 只翻译地址**：虚拟地址 → 物理地址，不负责复制文件数据。
- **mmap 的零拷贝**：主要省掉“页缓存 ↔ 额外用户缓冲区”的 CPU 拷贝，不是全链路没有数据移动。
- **MAP_SHARED / MAP_PRIVATE**：前者可回写文件，后者写时复制且不修改原文件。
